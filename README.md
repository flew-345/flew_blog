# Flew 个人博客

采用前后端分离架构的个人博客。本阶段先完成前端设计与交互，通过模拟数据独立运行；后续通过统一接口接入后端。

> 当前进度：已完成项目约定文档、Git 忽略规则与本地初始提交。尚未生成前端应用、安装依赖或接入后端。下文的页面、目录和接口均为后续实施约定，不代表已经完成。

## 1. 已确认的需求

- 建设一个用于发布文章、展示个人信息的个人博客。
- 采用前后端分离架构，前端可独立开发、构建和部署。
- 当前阶段优先完成前端页面设计与交互。
- 使用 Git 保存初始版本与后续改版，支持恢复到上一版或指定版本。
- 项目同步到 GitHub，保留可追溯的修改记录。
- 开发前先维护本 README，记录要求、注意事项和验收标准。

## 3. 第一阶段：前端范围

### 页面规划

| 页面 | 主要内容与交互 |
| --- | --- |
| 首页 | 博客简介、最新文章、分类或标签入口 |
| 文章列表 | 标题、摘要、日期、标签、分页 |
| 文章详情 | Markdown 正文、代码块、文章目录、上一篇与下一篇 |
| 分类与标签 | 按分类或标签筛选文章，支持直接访问筛选结果 |
| 归档 | 按年份和月份浏览文章 |
| 搜索 | 在当前模拟文章集合中搜索标题、摘要与标签 |
| 关于 | 个人介绍、技术方向和有效的外部链接 |
| 404 | 清晰的提示和返回首页入口 |

### 交互与视觉要求

- 桌面、平板、手机均可使用；至少检查 375px、768px、1440px 三档宽度。
- 导航、按钮、链接、筛选、分页和主题切换应有实际交互。
- 页面风格保持一致：统一颜色、字号、间距、圆角和组件状态。
- 文章正文优先保证阅读舒适度，避免正文过宽、字号过小和长段落拥挤。
- 代码块、表格和长链接在小屏幕上正确处理溢出，避免整个页面横向滚动。
- 提供加载、空内容、搜索无结果、文章不存在和请求失败状态。
- 使用语义化 HTML；支持键盘操作、可见的焦点、图片替代文本及合理的文字对比度。
- 动画保持克制，并尊重系统的减少动态效果设置。
- 为页面设置有意义的标题与描述。若上线时需要完整的搜索引擎收录与分享预览，应另行评估预渲染或服务端渲染方案。

### 当前阶段不包含

- 后端服务、数据库和真实的文章发布能力。
- 登录注册、管理后台、评论提交、文件上传等需要服务端支持的功能。
- 真实访问统计、邮件订阅或第三方账号授权。

如需预览上述功能，应明确标注为演示，不展示虚假的提交成功或真实数据。

## 4. 前后端分离约定

- 页面组件不直接绑定模拟数据文件或固定后端地址，统一通过服务层读取数据。
- 模拟数据与真实接口应遵循相同的类型定义，便于后续切换。
- API 基地址通过环境变量配置，例如 `VITE_API_BASE_URL`；提供不含秘密的 `.env.example`。
- Vite 的 `VITE_` 变量会暴露在浏览器中，不能存放密码、私钥或服务端令牌。
- 接口请求集中处理超时、取消、错误提示和响应解析。
- 跨域策略与身份认证方式在接入后端时共同确定；开发代理不代表生产环境已配置跨域。
- 如需渲染 Markdown 内的 HTML，必须进行内容净化；默认不直接渲染未经处理的 HTML。

建议接口如下，最终以双方确认的接口文档为准：

| 方法与路径 | 用途 |
| --- | --- |
| `GET /api/v1/posts` | 文章列表；支持 `page`、`pageSize`、`category`、`tag`、`q` |
| `GET /api/v1/posts/:slug` | 获取文章详情 |
| `GET /api/v1/categories` | 获取分类 |
| `GET /api/v1/tags` | 获取标签 |
| `GET /api/v1/archives` | 获取按年月分组的归档 |
| `GET /api/v1/profile` | 获取站点和个人资料 |

文章列表建议返回 `items`、`total`、`page`、`pageSize`。列表与详情应区分摘要和正文，约定稳定的文章 `id`、唯一 `slug` 以及带时区的 ISO 8601 日期。

## 7. Git 版本管理与回退

### 保存版本

- 默认使用 `main` 分支保存可交付版本。
- 每次改版前确认工作区状态；已有未提交成果应先整理保存。
- 每轮可交付改版创建独立提交，提交信息说明具体改动；较大改版可使用 `feat/主题` 分支。
- 对已确认的里程碑使用标签，例如 `v0.1.0`，便于精确定位。
- 推送成功前，本地提交不等同于 GitHub 备份。

```bash
git status
git diff
git add README.md
git commit -m "docs: update blog requirements"
git log --oneline --decorate -10
```

上面的暂存命令仅演示 README 修改；实际提交时按本次改动明确选择文件，并检查暂存差异。

### 不满意时回退

已经提交并共享的版本，优先使用 `git revert` 创建撤销提交，保留历史：

```bash
# 先确认工作区干净，再查找本轮改版的提交
git status
git log --oneline --decorate -10

# 撤销一个普通提交；把 COMMIT_ID 替换为实际提交编号
git revert COMMIT_ID
```

如果上一轮改版恰好只有最新的一个普通提交，可用 `git revert HEAD`。若包含多个提交、合并提交或发生冲突，应先核对改动范围再处理，不能假定一个命令就能恢复完整版本。

仅预览某个旧版本时，可在工作区干净后使用 `git switch --detach COMMIT_OR_TAG`；结束后用 `git switch main` 返回。若需要基于旧版本继续修改，应先创建新分支。

不默认使用 `git reset --hard`、清理未跟踪文件或强制推送，以免丢失未保存成果或覆盖远端历史。

## 8. GitHub 同步

GitHub 仓库：[flew-345/flew_blog](https://github.com/flew-345/flew_blog)。仓库可见性沿用现有设置。

首次配置远端并推送的命令如下。若本地已经配置 `origin`，先检查地址，不重复添加：

```bash
git remote add origin https://github.com/flew-345/flew_blog.git
git remote -v
git push -u origin main
```

如果已经存在 `origin`，先核对地址；如果远端已有提交，先检查并整合双方历史，不直接覆盖。后续每次提交确认后使用 `git push`；标签需另外执行 `git push origin TAG_NAME`。

需要在当前机器具备对应仓库的写入权限。认证应通过 Git 凭据管理器、SSH 或 GitHub CLI 等方式完成，访问令牌不得写入 README、代码或提交历史。
